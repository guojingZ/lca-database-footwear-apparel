# 覆盖升级指南

## v0.1.0 → v0.2.0：直接覆盖

1. 在旧服务终端按 Ctrl+C 停止 Python。
2. 解压新版 ZIP，打开里面的 `lca-database-footwear-apparel-main`。
3. 将其全部内容复制到你现有同名项目根，允许覆盖同名文件；包含 `.gitignore`、`.gitattributes`。不要多套一层目录。
4. 保留 `.git/`、`.venv/`、`venv/`、`.env`、`local-data/` 和个人资料。本轮没有需要删除的路径。
5. 运行下方校验，再启动。打开默认新人入门，或 `/demo` 独立演示。

```powershell
python tools/data_workbench.py validate
python app.py
```

本轮不需要运行 `prepare_upgrade.py`；它用于最初上游旧目录盘点，不是已有中文应用更新的前置条件。若页面找不到新版接口，先确认停止旧进程并重新启动服务。

个人保存模型的 catalog_digest 保持不变；计算规则和原始来源未改变。浏览器学习进度只在本机，不修改你的模型文件。

以下是首次从原始上游目录整理为中文应用时的历史操作说明；已经完成迁移的用户不必再执行。


适用对象：原始 `lca-database-footwear-apparel-main` 已在你的本地 Git 管理，新版压缩包提供同名顶层目录。你的实际分支、未提交改动和个人新增文件未知；本工具按原始哈希与严格的换行等价规则盘点，不假装已检查你的电脑。

2026-10-04 迁移修订：旧工具将 CRLF/LF 差异一律判为修改；修正版单列仅换行不同的文件，保留其本地原字节备份。中文应用与核算仍为 v0.1.0。

## 推荐操作顺序（Windows）

### 1. 先保存本地状态

在旧项目检查：

```powershell
git status --short
git diff --stat
```

按你现有 Git 流程保存未提交工作，并确认个人资料有备份。不要把 `.env`、环境或私人模型提交到仓库。可以建立本次升级分支，名称自行选。

### 2. 新包先解压到另一个临时目录

例如旧项目为 `D:\Projects\lca-database-footwear-apparel-main`，新包先解压到 `D:\Temp\carbonfact-v0.1\lca-database-footwear-apparel-main`。两者不要重叠，先盘点再覆盖。

在**新版临时目录**运行：

```powershell
python tools/prepare_upgrade.py --target "D:\Projects\lca-database-footwear-apparel-main"
```

结果含匹配旧文件、仅换行不同的文件、改过的旧来源、旧目录额外文件、新版同名路径冲突、已是新版的根文件和缺失旧文件。`can_apply=true` 表示工具未发现已登记路径冲突，不代表未知个人文件已被你审阅。

| 输出字段 | 怎样判断 |
|---|---|
| `matching_old_files` | 可以备份的旧文件，包括原字节一致和仅 CRLF/LF 不同两类 |
| `line_ending_only_files` | 上一项的子集；已验证只差 CRLF/LF，正文与其他字节不忽略 |
| `modified_source_files` | 有其他差异或路径异常；整次迁移停止，不自动丢弃修改 |
| `new_application_path_conflicts` | 新版要写入的路径已有不同内容；先备份与合并 |
| `can_apply` | `true` 才能进入工具备份；`false` 时不移动任何文件 |

`modified_source_files` 或 `new_application_path_conflicts` 非空时，工具不会移动任何文件。先把那些文件复制到你自己的备份目录，对照本包的原始上游或新版应用文件合并；不要为通过检查而直接丢掉修改。处理同名冲突后重新盘点。

### 3. 将匹配旧文件移到备份

```powershell
python tools/prepare_upgrade.py --target "D:\Projects\lca-database-footwear-apparel-main" --apply
```

工具只把与上传快照原字节一致或仅 CRLF/LF 不同的旧位置文件移到旧项目内 `_upgrade_backup/<时间>/`。**不会改写本地文件的换行，也不会改写新版上游快照。** 每个备份文件的实际 SHA-256 记录在 `备份说明.json`。它保留 `.git`、环境、个人文件以及未知文件；只移除已经空的旧来源目录。执行前及逐文件移动前再次检查本地原字节，失败时尝试回滚已移动内容。

重复执行在无匹配旧文件时不继续移动。**不要对 `_upgrade_backup` 内容运行该工具；该目录是可恢复的备份。**

### 4. 覆盖新版内容并验证

复制新解压目录的**内容**到旧项目根，避免复制出第二层同名目录。也要复制根 `.gitignore` 和 `.gitattributes`；包里没有 `.git`，所以不替换 Git 历史。`.gitattributes` 对 `upstream/carbonfact/` 禁用 Git 换行转换，以保留快照原字节；原始来源校验仍要求逐字节一致。对于此前未知的同名个人文档，先确认合并，不强行覆盖。

```powershell
python tools/data_workbench.py validate
python -m unittest discover -s tests -v
python app.py
git status --short
git diff --stat
```

验证通过后按你的 Git 流程提交重构。Git 可能显示大量删除/新增，部分自动识别为移动，这是目录迁移的正常表现。工具备份默认被 `.gitignore` 排除，仍保留在磁盘上供恢复。

## 覆盖后还看到旧目录怎么办

覆盖复制不会删除旧文件。若已经先复制了新版，再运行工具盘点，旧来源目录仍可按哈希备份；新版发布标记与同名根文件会按发布清单识别。若只复制了部分新版文件，执行后应再复制新版内容，确保根文件齐全。

如工具发现源文件改过，保留新旧两份后人工合并，不使用 `git reset --hard` 或强制目录删除。不要清理你自建的 `.github`/`.claude` 内容。

## 大量文本被旧工具报告为修改怎么办

若 PDF 正常、Markdown/配置/部分 CSV 被报告为修改，可能是 Git 或编辑器将上传快照的 CRLF 换行转换成 LF。这是待检查的原因，不能仅凭文件类型认定你没有真实修改。

下载迁移修订包并解压到**另一处临时目录**，在修订包目录重新运行盘点，不先覆盖你的旧项目：

```powershell
python tools/prepare_upgrade.py --target "C:\Tool\Code\Project\AI_code\lca-database-footwear-apparel-main"
```

如果 `modified_source_files=[]`、`new_application_path_conflicts=[]`、`can_apply=true`，使用同一命令加 `--apply`，随后按步骤 4 覆盖修订包的内容。`line_ending_only_files` 非空本身不阻止备份。

若仍有 `modified_source_files`，将名单里的本地文件与修订包 `upstream/carbonfact/` 中同路径文件对照，先保存真实修改，再决定迁移和合并。修正版不忽略数值、正文、行尾空格、BOM、多出来的换行或单独 CR，也不对 PDF 做换行等价匹配。不要通过改哈希清单、全局修改 Git 换行配置或强制删除来绕过检查。

## 回滚与未来更新

回滚优先使用你升级前保存的 Git 状态；备份目录也保留原路径内容，可按需复制回来，但不要覆盖升级后新产生的个人模型。备份验证与 Git 提交都完成后，你可以自行决定何时删除 `_upgrade_backup`，本工具不会自动删除它。

此后更新上游只更新来源层并登记差异；不能通过重置整个工作区把中文应用覆盖掉。中文应用自身升级按新版本迁移指南进行。
